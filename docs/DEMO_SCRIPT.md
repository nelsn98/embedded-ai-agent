# 2–4 分鐘 Demo 腳本

## 錄影前

完成 500ms、1000ms 兩組單一入口驗收，保存各自 report.json。
關閉會佔用 COM4 的 monitor。將 API Key 和 .env 從畫面移開。
畫面包含終端、外接 LED、最後的報告摘要。

## 展示順序

1. 約 20 秒：說明「這個專案讓 Gemini 透過受限制工具修改 ESP32 韌體，並用設備日誌驗證需求」。
2. 約 60–120 秒：執行 README_DAY3 的 1000ms 命令，展示三個 TOOL 結果，輸入 FLASH，RESET，等待 DEMO PASS。
3. 約 20 秒：開啟 summary.md，說明期望值、驗證結果、LED 每次切換間隔。
4. 約 30–60 秒：執行錯誤期望的 Pipeline，展示 FAIL: verify；說明編譯成功不等於符合需求。
5. 約 20 秒：說明工具只改一個參數、需要燒錄確認、保留執行證據，後續可加入更完整韌體功能。

實際片長取決於 API 及編譯速度；可以剪輯等待段，但應標示。

## 面試可說明的設計決策

- 自然語言由 LLM 轉成工具參數，驗收值由 CLI 獨立提供。
- 工具執行順序與成功狀態由 Python 檢查。
- Build 成功後才詢問燒錄，取消不會執行 Flash。
- 在 BOOT_OK 同步後才量測，避免把 RESET 前後時間戳混在一起。
- 驗證使用韌體時間戳，主機 UART 延遲不直接當作 GPIO 時序。
- 後續重啟、格式錯誤及間隔錯誤都不能通過。
- 目前是有限範圍的韌體研發自動化 PoC，尚未具備自動修復或端側模型推論。
